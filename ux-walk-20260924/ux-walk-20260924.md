# ux-walk-20260924

Walk of `mini-coder` 0.8.0 (working tree, commit `7841cb1`) driven by hand through tmux,
observed only. Everything the walk produced is in the untracked `ux-walk-20260924/`
directory (`captures/`, `shots/`, byte logs, `sessions/`). No source was changed.
The same material is grouped state-by-state with its images in
`ux-walk-20260924/presentation.html`.

## Harness

- App: `node /home/xonecas/src/agents/mini-coder/src/cli.ts`, cwd = `ux-walk-20260924/`,
  so `sessionsDir` (unset) resolved to `ux-walk-20260924/sessions/` — 12 sessions, all there.
  The repo's `sessions/` gained nothing (its six `20260924-*` dirs all predate this run) and
  `git status` shows only the run dir and the pre-existing `ux-walk.md`.
- Terminal: tmux 3.7c pane inside a kitty window sized in cells to the pane
  (`window-size manual` + `resize-window`), client `TERM=xterm-kitty`, pane `TERM=tmux-256color`,
  tmux status line off so pane height == client height. Geometry is recorded per capture and
  re-read with `tmux display -p '#{pane_width}x#{pane_height}'` next to every image.
- Keys: `send-keys -l` for literal text, named keys for `Enter/Escape/C-c/C-d/BSpace/DC/Tab/…`,
  `set-buffer` + `paste-buffer -p` for real bracketed pastes. `extended-keys on` plus
  `terminal-features *:extkeys` on the client.
- Byte logs: one `script -q -O <log> -c 'node …/cli.ts'` per app instance inside the pane
  (`s01.log` … `s16.log`, plus `ro/pf.log` for the persistence-failure run).
- Images: `spectacle -a -b -n` per state, verified with `identify` and looked at.
  Cell ≈ 9.0 × 22 px; a 100×30 pane grabbed 903×691 px.
- Provider/model: as configured, `opencode-go/deepseek-v4.1-flash`, effort `medium`.
  Reasoning *is* produced by this model at that effort (verified in `sessions/*/session.jsonl`
  and in the dim in-flight preview), but with `thinkingLevelMap.medium = null` the request
  carries no thinking level, so reasoning appears only for some prompts.
- Hazard seen once and worked around: with a live turn, the model's own `bash` tool can reach
  this pane (`tmux send-keys`), so prompts must be self-contained. One session (`s07`) started
  with a stray line typed into the running app because the app was still alive from the
  previous geometry; that session's captures are still valid (the tool runs, pauses and
  resizes were real) but its byte log is `s06-1x1.log`, not `s07.log`.

### Not covered

- `! <provider error>`: not reachable with the configured provider without breaking auth/network,
  so it is reported as not covered rather than faked.
- `read` of an image on a model that does *not* accept image input (`read failed: … does not
  accept image input`): requires changing `provider`/`model`, which the walk does not allow.
- The `preparing` and `waiting for provider` status rows: never observed — see finding 2.
- The model-facing `... output truncated ...` marker from `tools/bash.ts`: it lands inside the
  elided middle of the body and is therefore never visible; only the display marker
  (`... N lines not shown ...`) is reachable.
- A copy out of the terminal was exercised with tmux copy-mode (`begin-selection`/`copy-selection-and-cancel`
  → `show-buffer`): plain text, no escapes. The elision marker appears in copied text as the
  literal `... N lines not shown ...` row.
- Startup race: once, two characters sent immediately after launch were lost (the app was still
  in canonical mode). A 500-character burst after the banner appeared showed no loss, so this
  is reported as an unreproduced observation, not a finding.

## Findings

### 1. Raw control bytes in tool output rewrite and erase committed scrollback (major, breaks a stated contract)

**Doing:** asking the agent to run ordinary commands whose output contains escape sequences —
progress bars, `clear`, `\r` redraws, colourised tools.
**Keys/timing:** `Run bash exactly: printf '\033[5A CURSOR MOVED UP\n'` then `Enter`.
**What appeared:** the row five lines above the tool body was overwritten:

```
[co CURSOR MOVED UP
```

the previous turn's `[complete · 3s]` line became `[co CURSOR MOVED UP`, i.e. a committed
scrollback row was rewritten. With `printf '\033[2J'` the whole visible screen — every earlier
block — was erased, leaving a blank pane with only the new tool line; with a bare `\r` the tool
body's ` | ` marker is eaten and the row realigns under column 1:

```
 | col1    col2
overwrite
```

![cursor-up injection](ux-walk-20260924/shots/s03-bash-cursorup-100x30-26.png)
![clear-screen injection](ux-walk-20260924/shots/s03-bash-clearscreen-after-100x30-25.png)

**Should have appeared:** the tool's text, with control characters escaped or filtered so a
result can only add rows, never move the cursor or erase what is already on screen.
**Smallest reproducer:** one turn, `printf '\033[5A X\n'`, at 100×30.
**Evidence:** `captures/s03-bash-cursorup-100x30-26.txt` (raw bytes contain the unescaped
`\x1b[5A` inside the body row), `captures/s03-bash-clearscreen-after-100x30-25.txt`,
`captures/s03-bash-hostile-100x30-23.txt`.
**Contract:** the walk's own scrollback-integrity requirement ("nothing rewritten or lost"); the
TUI also owns nothing else here — the body is written unstyled and unfiltered. Fix line: escape
or drop non-SGR control bytes at the tool-result boundary.

### 2. `preparing` and `waiting for provider` are unreachable, and the row says "streaming" during the provider wait (minor, latent state)

**Doing:** pressing `Enter` and watching for the first feedback.
**Keys/timing:** 30-frame burst at 80 ms from `Enter`, then a 10 ms-resolution poll around `Enter`.
**What appeared:** the first frame already reads `⠋ streaming · 0s · ctx 410/1M · 0%`
(69 ms after `Enter`); no frame ever showed `preparing` or `waiting for provider`. In
`src/agent.ts` the `waitingModel` phase is emitted when the stream object is constructed and
`streaming` is emitted immediately after, i.e. before the HTTP request, so the whole network
wait is labelled "streaming" and the label that describes it never renders.
**Should have appeared:** either a phase label that covers the first-byte wait, or no such state.
**Smallest reproducer:** `Enter` on any prompt, capture every 80 ms; frame 1 is already `streaming · 0s`.
**Evidence:** `captures/s03-phases-100x30-01`.
**Contract:** the phase list in `AGENTS.md`/code is the contract; two of its values are dead.
Taste call on which label to use.

### 3. Every terminal resize leaves a ghost status row in scrollback and unpins the live region (major)

**Doing:** resizing the window (or the tmux pane) with the app idle.
**Keys/timing:** fresh app at 100×30, then one `resize-window -y 29`.
**What appeared:** before — one status row; after — two, the stale one kept in scrollback with a
blank row under it, the live one drawn below:

```
mini-coder · opencode-go/deepseek-v4.1-flash
ctx 404/1M · 0%          <- live (before)
ctx 404/1M · 0%          <- ghost (after one resize)
ctx 404/1M · 0%          <- ghost (after two)
```

Nine resizes in one session produced nine stacked status rows
(`shots/s06-fresh-idle-200x50.png`), and after growing the pane the live region is no longer at
the bottom of the screen — status and editor sit mid-screen with empty rows below them, because
`handleResize` drops the anchor (`live.reset()`) and the next frame re-emits the region at the
cursor's current position instead of over the old one.

![three stacked status rows](ux-walk-20260924/shots/s06-resize-after-100x28-03.png)
![region above the bottom after growing](ux-walk-20260924/shots/s07-stream-done-100x30-04.png)

**Should have appeared:** one status row, and a live region that stays at the bottom of the pane.
**Smallest reproducer:** fresh app, one row smaller, one row back: 1 → 2 → 3 status rows.
**Evidence:** `captures/s12-resize-clean-before-01.txt`, `captures/s12-resize-clean-after-02.txt`,
`captures/s06-resize-before-100x30-02.txt`, `captures/s06-resize-after-100x28-03.txt`.
**Contract:** `AGENTS.md` "no full-screen buffer … no live region left behind" and the walk's
"exactly one blank row between blocks"; the ghosts also grow the scrollback on every resize.
Fix line: erase the tracked region (or re-anchor it deterministically) on resize.

### 4. Shift+Enter submits the draft instead of inserting a newline under tmux (major, environment-dependent; breaks the pinned keybinding)

**Doing:** adding a second line to a draft, as `/help` advertises.
**Keys/timing:** type `one`, `Ctrl+J`, `two`, then `Shift+Enter` via tmux (extended keys on,
`terminal-features *:extkeys`, client `xterm-kitty`).
**What appeared:** no newline — the whole draft was submitted and the model started answering:

```
> one
> two
> three
The user's message is just "one two three". That's ambiguo…
⠼ streaming · 1s · ctx 408/1M · 0%
```

A byte probe run in the same pane shows what the app receives: with `extended-keys off`
`S-Enter` → `"\r"`; with `extended-keys on` + `extkeys` → still `"\r"`. Feeding the kitty
encoding directly (`send-keys -l $'\x1b[13;2u'`) *does* insert a newline, and `Ctrl+J` does too,
so the parser is fine and the key simply never arrives in this terminal stack.
**Should have appeared:** a newline in the draft; the user asked for one and got a submission.
**Smallest reproducer:** `mini-coder` inside tmux inside kitty → type `a`, press `Shift+Enter`.
**Evidence:** `captures/s08-shiftenter-on-12.txt`, `captures/s08-shiftenter-submits-15.txt`,
`captures/s08-extkeys-off-bytes-11.txt`, `captures/s08-ctrlj-newline-13.txt`,
`captures/s08-csiu-shiftenter-14.txt`; probe script `ux-walk-20260924/probe-keys.mjs`.
**Contract:** `/help` prints `Shift+Enter newline (Ctrl+J also works)`. Fix line: drop the
Shift+Enter claim where the sequence cannot arrive, or state the tmux/terminal requirement.

### 5. The one dark theme is applied inconsistently: the chrome is left to the terminal (major, legibility)

**Doing:** reading the status row, a tool body, a fence and a heading on a light-background
terminal (`background #fbf7ee`, `foreground #101010`).
**What appeared:** every `SGR 2` element is near-invisible on the light background — the status
row (`ctx 1.4k/1M · 0%`), the `[complete · 5s]` line, the ` | ` body prefixes — and the
hardcoded TokyoNight-moon truecolor tokens wash out or invert: the js fence body renders in pale
pastels on cream, `# Hello` as blue on a dark navy tint, `` `inline code` `` as a dark chip.

![light theme tool body](ux-walk-20260924/shots/s10-light-tools-100x30-02.png)
![light theme markdown](ux-walk-20260924/shots/s10-light-markdown-100x30-03.png)

The split is systematic, not per-row: the rows that carry palette colours are exactly the rows
that do not follow the terminal (markdown spans, fence bodies, diff lines), and the rows written
with default foreground plus `SGR 2` are exactly the chrome rows (status readout, ` | ` markers,

### 8. Esc is silent, and in a tool-less turn it is silently dropped (minor)

**Doing:** pressing `Esc` during a streamed reply to pause the agent.
**Keys/timing:** `Esc` at t+1.5 s, then poll every 500 ms.
**What appeared:** nothing for 1.5 s — the row kept spinning (`⠧ streaming · 2s`); the pause
row only appeared when the next step boundary was a tool call. In a turn with no tool calls the
request is discarded at the end of the turn and the user sees it run to completion:

```
t+1.5s Esc           → ⠼ streaming · 2s
t+2.0s               → paused - type steering, Enter to submit   (tool call pending)
```

vs. the tool-less turn, where the same `Esc` produced `[complete · 7s]` and never paused.
**Should have appeared:** an acknowledgement that the pause is pending (the phase machinery has a
`pausing` value that only fires later), and either a pause or a clear "nothing to pause".
**Smallest reproducer:** `Esc` while a tool-less reply streams.
**Evidence:** `captures/s03-paused-streaming-100x30-03.txt`, `captures/s03-paused2-100x30-05.txt`,
`captures/s03-esc-in-runningtool-100x30-17.txt` (Esc during a tool waits for the tool, ~10 s).
