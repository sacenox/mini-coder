How the walk was produced

instrument
tmux 3.7c pane inside a kitty window sized in cells to the pane (window-size manual + resize-window); status line off so pane height equals client height. Geometry re-read for every capture (tmux display -p '#{pane_width}x#{pane_height}') and recorded in the artifact name.
client TERM=xterm-kitty, pane TERM=tmux-256color, cell ≈ 9.0 × 22 px, a 100×30 pane grabbed 903×691 px.
input
send-keys -l for literal text, named keys for Enter/Escape/C-c/C-d/BSpace/DC/Tab/…, set-buffer + paste-buffer -p for real bracketed pastes. extended-keys on plus terminal-features *:extkeys on the client.
record
one script -q -O <log> -c 'node …/cli.ts' per app instance inside the pane — that log is the only artifact showing the erase and redraw traffic actually emitted.
judge
spectacle -a -b -n per state, identify-checked and looked at; text captures are capture-pane -p -e -S -, so scrollback and styling are in them.
cwd
ux-walk-20260924/, so sessionsDir (unset) resolved to ux-walk-20260924/sessions/. The repo and ~/.config/mini-coder were untouched.

one hazard worth knowing

The agent under test has bash and the walk ran inside a tmux pane, so a chatty prompt lets the model reach the pane that hosts it. Prompts were kept self-contained after one session started with a stray line typed into the running app; that session's captures are still valid (the tool runs, pauses and resizes were real), only its log name is off (s06-1x1.log, not s07.log).

what "background" means here

The app ships one dark theme. The palette is TokyoNight moon for markdown, fences and diffs, while the chrome — status row, | body markers, > echo, [complete · Ns] and the terminal-state lines — is written with default foreground and SGR 2. That distinction is what the light-terminal pass (and finding 5) is about: not "no light theme", but the one theme not applied everywhere.

Reasoning: the configured model does emit thinking blocks, but thinkingLevelMap.medium = null, so the request carries no thinking level and the dim in-flight preview only appears on prompts the model decides to reason about.

theme pass — the same states on a terminal that is not dark

Light-terminal pass

The point of these three captures is not "there is no light theme" — mini-coder ships one dark theme. It is that the theme is applied to some rows and not to others, so on a terminal whose background is not the theme's the halves disagree.

what the eye gets on a light background:
  ctx 1.4k/1M · 0%        SGR 2 on default fg  -> nearly white on cream
  [complete · 5s]         SGR 2 on default fg  -> nearly invisible
   | alpha                the marker is SGR 2, the text is default fg
  ```js / const x = 1;     TokyoNight moon pastels on cream
  # Hello                 blue fg on a dark navy tint
   ! exit 4               no SGR at all -> the most readable row

the marks that carry colour are exactly the ones that do not follow
the terminal; the marks written with SGR 2 / default fg are exactly
the chrome rows. Hence: one theme, applied inconsistently (finding 5).

Nothing here is a request for a second theme — it is the same defect the report files as finding 5: chrome rows and terminal-state lines are handed to the terminal's defaults, while markdown/diff spans are painted from the hardcoded palette, so the two styles contradict each other on any background that is not the palette's own.

idle on light · report → finding 5

Same palette, dark terminal: tool body · markdown — the rows that look "fine" there are the ones carried by the theme; the dim ones are carried by the terminal.

user was doing
resizing the window, or letting the WM do it, with the app idle and with turns in flight.
appeared

expected
one status row, and after the pane grows the region back at the bottom, not mid-screen.
why
handleResize() drops the anchor (live.reset()), so the frame after the resize cannot erase what the previous frame drew; the tracked row count no longer describes the screen.

finding 5 · corrected framing

The dark theme is not applied consistently major legibility

There is one theme and it is dark. The defect is that only part of the UI is painted with it: markdown, fences and diffs get explicit TokyoNight moon colours, while the chrome — status row, | body markers, > echo, [complete · Ns], terminal-state lines — is written as default foreground and SGR 2, i.e. whatever the terminal's background happens to be.

row                                        written as            follows
ctx 1.4k/1M · 0%         status row         SGR 2 + default fg    terminal
[complete · 5s]          terminal state     SGR 2 + default fg    terminal
 | alpha                 tool body marker   SGR 2 + default fg    terminal
> prompt                 user echo          default fg            terminal
! cancelled              terminal state     no SGR at all         terminal
@@ / + / - / context      diff rows          cyan / green / red   theme
# Hello / `code`         markdown           palette + bg tint     theme
js fence body            code               palette               theme

the contradiction is structural, not cosmetic: half the screen
descends from the palette and half from the terminal, so the two
halves can never agree on any background the palette does not own.
user was doing
reading the same states on a terminal whose background is not the theme's dark one.
appeared
chrome rows effectively invisible, palette rows washed out or inverted; the only fully readable line was the error marker that carries no style at all.
expected
one theme applied to every row it styles — chrome included — so the UI looks the same wherever it runs.
severity
major: the context readout, the completion line and the block markers are the rows a user scans.
note
this is not a request for a light theme; it is the inconsistency between the two style sources inside the single theme.

What the walk could not reach

states that need a different configuration or a broken provider

  • ! <provider error> — the configured provider answered on every turn; forcing an error means breaking auth or the network, which the walk does not do. Reported as not covered rather than faked.
  • read on a model without image input — the branch that returns read failed: … does not accept image input needs a text-only provider/model, i.e. a config change; the image-capable path was captured instead.
  • the model-facing ... output truncated ... marker from tools/bash.ts — it lands inside the elided middle of the body, so it never reaches the screen; only the display marker ... N lines not shown ... is reachable.
  • preparing / waiting for provider — not a coverage gap in the harness: the rows cannot be rendered at all (finding 2).

one unreproduced observation

Immediately after one launch, two characters sent within the first moments were lost — plausibly the window before the app puts the tty in raw mode. A 500-character burst sent after the banner rendered lost nothing, so it is recorded as an observation, not a finding.

how the copy path was checked

A selection made in tmux copy-mode (begin-selection … copy-selection-and-cancel) and read back with show-buffer yields plain text with no escape noise; an elision marker in the selection appears as the literal row ... N lines not shown ..., which is how the display marker stays distinguishable from file content.
